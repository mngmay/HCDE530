# Week 2 — Competency 2: Code literacy and documentation

## Observations

For me, **code literacy** in this class is not about memorizing syntax—it is the ability to **understand the structure and intent of code**: what the script is trying to do, how data moves through it, and why pieces are organized the way they are.

### Code literacy

- Re-familiarizing myself with **Python** (`.py` files) helped reinforce basic structure and syntax: functions, loops, reading CSVs, and how small scripts turn raw data into readable output.
- **Git and GitHub** felt like the most “developer” part of the week; they also helped me build a clearer **mental model** of how my editor, local folders, and a remote repo relate to each other.
- Working with **AI-assisted coding** strengthened another kind of literacy: learning to **prompt for useful code**, **interpret what it generated**, **ask follow-up questions**, **make targeted edits**, and **debug errors** when something did not run as expected.

### Documentation

This week I paid attention to documentation as **communication**, especially:

- **Comments** in code (what a block or function is for),
- **README-style explanation** (how someone else—or future me—would run or understand the project),
- **Cursor rules** (`.cursorrules`) as lightweight “team defaults” for how tools and collaborators should behave in this repo.

### Connection to this week’s work

The hardest moment was **keeping files organized when the end goal was still fuzzy**—without a clear target, it was easy to second-guess folder layout, naming, and what belonged in version control.

A concrete win was **getting installs and environment setup working smoothly**, which lowered the friction for everything else.

Overall, this week’s work supports Competency 2 by combining **readable code**, **explicit documentation habits**, and a growing comfort with the **toolchain** (editor, files, Git/GitHub) that makes iteration and collaboration possible.
